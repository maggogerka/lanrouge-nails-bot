# Установка экземпляра бота для нового клиента

Это внутренний регламент продавца и технического специалиста. Его не нужно выдавать мастеру как
инструкцию ежедневной работы. Здесь описано, что запросить у покупателя, как подготовить отдельный
экземпляр на Ubuntu 24.04 и как передать его владельцу.

## Важный production-стоп перед установкой

В текущей версии подтверждены два незавершённых Compose-подключения:

1. профили `api` и `reservation-worker` не получают PostgreSQL/Redis file secrets;
2. профиль `backup` не получает пароль PostgreSQL, а CI пока не выполняет настоящий
   backup → restore.

Поэтому до исправления и отдельной проверки нельзя обещать покупателю готовый Mini App/API,
автоматическое освобождение просроченных резервов или работающий production-backup в
документированном file-secret режиме. Для предоплаты автоматический reservation-worker является
обязательной частью эксплуатации. Базовый Telegram polling-бот и его основные workers используют
file secrets корректно.

Этот стоп снимается только после исправления Compose, зелёного CI smoke-теста профилей и
успешного восстановления резервной копии в отдельную тестовую БД.

## 1. Что согласовать с покупателем

### Данные бизнеса

- официальное и отображаемое название;
- описание, приветствие и логотип;
- телефон салона;
- адрес и отдельную HTTPS-ссылку на карту;
- часовой пояс и график работы;
- каналы клиентской поддержки;
- каталог услуг, длительности, цены и дополнения;
- перечень мастеров, их Telegram ID, услуги, фото, описание и контакты;
- реальные рабочие места и услуги, которые можно на них выполнять;
- дедлайны отмены и переноса, лимиты записи и расписание напоминаний.

### Юридические материалы

Покупатель или его юрист должен предоставить утверждённые документы, опубликованные по HTTPS:

- политику конфиденциальности;
- согласие на рекламную рассылку;
- оферту;
- правила отмены, предоплаты и возврата;
- реквизиты и сведения об операторе персональных данных, если это требуется применимым правом.

Кодовые шаблоны не заменяют юридическое заключение.

### Telegram и оплаты

- новый бот создаётся покупателем через `@BotFather`;
- покупатель передаёт token по защищённому каналу или сам помещает его на сервер;
- владелец присылает числовой ID из `/whoami`;
- для YooKassa нужны отдельные shop ID, secret, правила чеков и публичный HTTPS webhook;
- для ручной оплаты нужна инструкция без избыточных платёжных данных.

Не просите отправлять токены, пароли или платёжные секреты в обычный групповой чат.

## 2. Что заказать для одного бизнеса

Рекомендуемый стартовый VPS:

- Ubuntu Server 24.04 LTS x86_64;
- 2 vCPU;
- 4 GB RAM;
- не менее 30 GB SSD;
- статический публичный IP;
- ежедневные снимки VPS как дополнительная, но не единственная копия;
- отдельный домен, если понадобятся YooKassa webhook или API;
- отдельное S3-совместимое offsite-хранилище для резервных копий.

Для одного polling-бота входящие HTTP-порты не нужны. Порты 80/443 открывают только после
установки reverse proxy и TLS для webhook/API. PostgreSQL и Redis наружу не публикуются.

Каждому покупателю нужны отдельные VPS или как минимум отдельные Compose project name, каталог,
секреты, PostgreSQL volume, Redis namespace и backup repository prefix. Не смешивайте данные
разных покупателей.

## 3. Безопасный доступ к VPS

Попросите провайдера создать сервер и передать IP. Создайте отдельного пользователя развёртывания
с `sudo` и входом по SSH-ключу. Сначала проверьте вход по ключу, только затем отключайте парольный
вход и прямой вход `root`.

Не публикуйте Docker daemon на TCP-порту. Для удалённого управления используйте SSH или Docker
context через SSH. Официальная инструкция Docker:
<https://docs.docker.com/engine/security/protect-access/>.

Пользователь с доступом к Docker socket фактически имеет высокие полномочия на сервере. Не
выдавайте такой доступ мастерам и случайным подрядчикам.

## 4. Базовая подготовка Ubuntu 24.04

Подключитесь по SSH и обновите систему:

```bash
sudo apt update
sudo apt upgrade -y
# Замените Europe/Moscow на согласованный с бизнесом часовой пояс.
sudo timedatectl set-timezone Europe/Moscow
sudo reboot
```

После повторного входа установите Docker Engine и Compose plugin по актуальной официальной
инструкции: <https://docs.docker.com/engine/install/ubuntu/>. Не копируйте случайные install-скрипты
из блогов. Проверка после установки:

```bash
sudo systemctl enable --now docker
sudo docker run --rm hello-world
sudo docker compose version
```

Настройте firewall провайдера и Ubuntu. Оставьте SSH только со своего IP, если это возможно.
Учитывайте, что Docker управляет собственными firewall-правилами; правила для контейнерного
трафика проверяют через цепочку `DOCKER-USER` согласно документации Docker.

## 5. Получение приватного репозитория

Лучший вариант — read-only deploy key только для этого репозитория:

1. на VPS создайте отдельный SSH-ключ без отправки приватной части кому-либо;
2. добавьте публичную часть в GitHub как read-only Deploy key;
3. проверьте fingerprint GitHub;
4. клонируйте репозиторий в отдельный каталог, например `/opt/telegram-crm/client-name`;
5. зафиксируйте развёртываемый tag или commit SHA.

Не размещайте персональный GitHub token разработчика в `.env` приложения.

## 6. Секреты и `.env`

В каталоге экземпляра создайте `.env` из `.env.example` и отдельный каталог `.secrets`. Файлы
не должны попадать в Git или резервную копию исходников.

```bash
cp .env.example .env
mkdir -p .secrets
chmod 700 .secrets
openssl rand -base64 48 | tr '+/' '_-' | tr -d '=\n' > .secrets/postgres_password
openssl rand -base64 48 | tr '+/' '_-' | tr -d '=\n' > .secrets/redis_password
chmod 600 .env
chmod 644 .secrets/postgres_password .secrets/redis_password
```

Redis-пароль должен содержать только `A-Z`, `a-z`, `0-9`, `_`, `-` и иметь не менее 32 символов.
Compose file secrets являются read-only bind mounts. Каталог с режимом `0700` закрывает их от
других пользователей VPS, а режим файлов `0644` позволяет непривилегированному UID приложения
прочитать mount внутри контейнера. Не ослабляйте права родительского каталога.
В `.env` задайте как минимум:

- `BOT_TOKEN`;
- `ADMIN_TELEGRAM_IDS` для одноразового bootstrap первого владельца;
- `PRIVACY_POLICY_URL`;
- `DATABASE_URL` с правильными host/user/database и placeholder-паролем;
- `REDIS_URL` с правильными host/database и placeholder-паролем;
- уникальный `REDIS_NAMESPACE`;
- `VENDOR_SUPPORT_*` для связи владельца с вами;
- `SENTRY_DSN`, если мониторинг уже создан.

Compose подставляет фактические PostgreSQL/Redis пароли из файлов в основные application-
контейнеры. Значения секретов не выводите командами `cat`, `docker inspect`, в issue или чат.

## 7. Первая сборка базового бота

До запуска задайте уникальное имя проекта:

```bash
export COMPOSE_PROJECT_NAME=crm_client_name
export ENV_FILE=.env
export POSTGRES_PASSWORD_SECRET_FILE=.secrets/postgres_password
export REDIS_PASSWORD_SECRET_FILE=.secrets/redis_password
```

Проверьте конфигурацию и запустите базовый стек:

```bash
docker compose -f docker-compose.yml -f compose.production.yml config --quiet
docker compose -f docker-compose.yml -f compose.production.yml build
docker compose -f docker-compose.yml -f compose.production.yml up -d
docker compose -f docker-compose.yml -f compose.production.yml ps
docker compose -f docker-compose.yml -f compose.production.yml run --rm bot python -m app.healthcheck
```

Ожидаемый результат: PostgreSQL, Redis, bot и постоянные workers имеют `healthy`; `migrate`
завершился с кодом `0`; в логах бота есть начало polling.

```bash
docker compose -f docker-compose.yml -f compose.production.yml logs --tail 100 migrate bot
```

Не запускайте `docker compose down --volumes` на production: команда удаляет рабочую базу.

## 8. Первоначальная настройка владельца

1. Владелец отправляет `/whoami`.
2. Его ID один раз указывается в `ADMIN_TELEGRAM_IDS`.
3. Контейнер бота пересоздаётся.
4. Владелец открывает `/admin`.
5. После создания DB-роли доступ проверяется по базе, а не по постоянному env-списку.
6. Владелец проходит [«Запуск за 15 минут»](QUICK_START_15_MIN.md).

Проверьте отдельными Telegram-аккаунтами клиента, мастера и владельца. Нельзя считать проверкой
только наличие кнопки: нужно открыть карточку и выполнить безопасное тестовое действие.

## 9. Обязательная приёмка

До передачи выполните и запишите результат:

1. первое согласие клиента и отказ/согласие на рассылку;
2. запись с телефоном через кнопку Telegram и ручным вводом;
3. проверка длительности услуги и рабочего места;
4. просмотр записи владельцем и мастером;
5. перенос только на открытое окно;
6. дедлайн отмены и переноса;
7. ручная предоплата, подтверждение, отклонение и освобождение просроченного резерва;
8. напоминание клиенту;
9. завершение визита и отзыв;
10. отключение feature flag и исчезновение кнопки;
11. запрос удаления данных;
12. перезапуск каждого контейнера без потери рабочих данных;
13. резервная копия и восстановление в отдельную тестовую БД;
14. отсутствие секретов и персональных данных в логах.

Пункты 7 и 13 нельзя подписывать как пройденные, пока отмеченные в начале Compose-блокеры не
исправлены и не проверены.

## 10. Обновление и откат

Перед обновлением:

1. зафиксируйте текущий commit/tag и версию образов;
2. убедитесь в свежей offsite-копии и успешном restore-test;
3. прочитайте `CHANGELOG.md` и список миграций;
4. соберите новые образы;
5. выполните миграцию;
6. проверьте health и контрольную запись.

Не откатывайте код поверх уже применённой несовместимой миграции без отдельного плана. Откат
должен использовать заранее проверенный образ и совместимое состояние БД.

пароли — только факт передачи и ответственного владельца.

## 12. Как дать Codex доступ к VPS позже

Самый понятный вариант — подключиться к Ubuntu 24.04 через VS Code Remote SSH, открыть удалённый
каталог репозитория и запустить Codex в этом удалённом workspace. Тогда команды выполняются на
VPS, а не на локальном компьютере.

Подготовьте:

- IP или DNS сервера;
- отдельного пользователя развёртывания;
- SSH-ключ с минимально нужным доступом;
- путь к отдельному экземпляру проекта;
- возможность `sudo` только для согласованных административных действий.

Альтернативно можно создать локальный Docker context поверх SSH по официальной инструкции
Docker, но для правки файлов и диагностики Remote SSH удобнее.

Не присылайте пароль root, приватный SSH-ключ, `.env` или содержимое `.secrets` в чат. Ключ должен
храниться у вас локально. Сначала попросите выполнить read-only аудит (`docker compose ps`, логи,
версии, свободное место), затем отдельно разрешайте обновление, перезапуск или миграции. Доступ
можно отозвать удалением публичного ключа из `authorized_keys`.
