# Правила окон, бронирования, отмены и переноса

Статус: нормативное описание бизнес-правил v0.1.0. Если реализация расходится с этим документом, приоритет имеет явно согласованное более новое решение, отражённое одновременно в документации и тестах.

## 1. Термины

- **Окно** (`AvailabilityWindow`) — созданный мастером неделимый интервал `[start_at, end_at)`, доступный максимум для одной записи.
- **Активное окно** — окно в статусе `open`, `reserved` или `booked`; `closed` и `expired` не участвуют в выдаче клиенту.
- **Запись** (`Appointment`) — подтверждённая связь клиента, услуги и целого окна со snapshot услуги.
- **Локальная дата** — календарная дата `start_at` после преобразования в `BusinessSettings.timezone`.
- **Сейчас** — один переданный сервису timezone-aware instant; в пределах операции он не вычисляется повторно.
- **Активная запись для лимита** — запись, которая занимает дневную ёмкость согласно разделу 5.

Интервалы полуоткрытые: окно, заканчивающееся ровно в момент начала другого окна, не пересекается с ним, но дополнительно должен соблюдаться `minimum_gap_minutes`.

## 2. Настройки по умолчанию

| Настройка | Значение |
|---|---:|
| `timezone` | `Europe/Moscow` |
| `booking_horizon_days` | `31` |
| `cancellation_deadline_hours` | `36` |
| `max_appointments_per_day` | `2` |
| `default_window_duration_minutes` | `210` |
| `minimum_gap_minutes` | `60` |
| `allow_saturday` | `false` |
| `allow_sunday` | `false` |
| `reminder_offsets_minutes` | `[1440, 180, 60]` |

Числовые настройки должны быть положительными, reminder offsets — уникальными положительными целыми, отсортированными по убыванию при отображении. Изменение фиксируется в audit log.

## 3. Состояния

### 3.1. Окно

```text
open -------> booked -------> open       (допустимая отмена с переоткрытием)
  |              |----------> closed     (отмена без переоткрытия)
  |              |----------> expired    (после времени окна)
  +----------> closed
  +----------> expired
reserved ----> booked/open/closed/expired (зарезервировано для будущего расширения)
```

В клиентском flow v0.1.0 переход выполняется непосредственно `open -> booked` внутри одной транзакции. `reserved` хранится в enum для совместимости с заданной моделью, но не создаётся обычным сценарием и не является клиенту доступным.

`expired` устанавливается для незанятых окон, начало которых уже прошло. Просроченное окно считается недоступным даже до фонового обновления статуса.

### 3.2. Запись

```text
confirmed -> client_confirmed -> completed
     |              |----------> cancelled_by_client
     |              |----------> cancelled_by_admin
     |              |----------> no_show
     |              |----------> rescheduled
     +-------------------------> те же терминальные статусы
```

- `confirmed` и `client_confirmed` — будущие активные записи.
- `completed`, `cancelled_by_client`, `cancelled_by_admin`, `no_show`, `rescheduled` — терминальные состояния конкретной записи.
- Перенос закрывает старую запись как `rescheduled` и создаёт новую `confirmed`, связанную с предыдущей.
- Каждый переход добавляет `AppointmentStatusHistory`; начальная запись имеет `previous_status = NULL`.
- Физическое удаление Appointment запрещено.

## 4. Создание окна

Администратор передаёт локальные дату/время, необязательную длительность и внутренний комментарий. Отсутствующая длительность заменяется текущим `default_window_duration_minutes`. После преобразования в UTC операция в одной транзакции:

1. Проверяет существование и admin-доступ автора.
2. Проверяет положительную длительность и `start_at < end_at`.
3. Проверяет `start_at > now`.
4. Проверяет горизонт: локальная дата не раньше текущей локальной даты и не позже `today + booking_horizon_days` включительно.
5. Проверяет субботу/воскресенье по локальной дате и флагам разрешения.
6. Берёт advisory lock локальной даты.
7. Проверяет число активных окон этой даты по принятому в [assumptions.md](assumptions.md) правилу лимита.
8. Блокирует/читает соседние активные окна этой даты.
9. Запрещает пересечение: `new_start < existing_end AND existing_start < new_end`.
10. Для предыдущего окна требует `new_start - previous_end >= minimum_gap`.
11. Для следующего окна требует `next_start - new_end >= minimum_gap`.
12. Создаёт окно в `open` либо `closed` и audit event.

Комментарий администратора клиенту никогда не отображается и полностью не логируется.

Закрыть можно свободное `open` окно. Занятое окно сначала обрабатывается как административная отмена/перенос записи. Hard delete допустим только для никогда не связанного с записью свободного окна; предпочтительное действие UI — `closed`, сохраняющее audit trail.

## 5. Доступность и дневной лимит

Клиент видит окно, только если одновременно:

- принято privacy consent;
- услуга активна;
- окно имеет статус `open`;
- `start_at > now` и окно не просрочено;
- `service.duration_max_minutes <= window duration`;
- локальная дата остаётся в актуальном горизонте;
- дневной лимит ещё не исчерпан.

Показ — только подсказка. Все проверки повторяются при подтверждении.

Дневная ёмкость сериализуется по локальной дате. В лимит записей входят `confirmed`, `client_confirmed`, `completed` и `no_show`; `cancelled_by_client`, `cancelled_by_admin` и `rescheduled` не входят. Так завершённый или no-show визит всё равно учитывает фактически использованную дневную ёмкость.

## 6. Транзакционное бронирование

Порядок блокировок обязателен:

1. Начать PostgreSQL transaction.
2. Получить transaction-level advisory lock для локальной даты окна.
3. Загрузить окно через `SELECT ... FOR UPDATE`.
4. Загрузить клиента и услугу; проверить consent и активность услуги.
5. Повторно проверить `window.status == open`, будущее время и вместимость по `duration_max`.
6. Посчитать записи дня, входящие в лимит; потребовать `count < max_appointments_per_day`.
7. Создать Appointment со snapshot названия, `Decimal`-цены и обеих длительностей.
8. Перевести окно в `booked`.
9. Добавить начальную status history.
10. Создать только будущие notification jobs с уникальными ключами.
11. Зафиксировать transaction.

Уникальное ограничение БД дополнительно не позволяет иметь более одной незакрытой записи на одном окне. Конфликт после конкурентной попытки превращается в сообщение: «К сожалению, это время только что заняли. Выберите другое свободное окно».

Если отправка сообщения после commit не удалась, запись остаётся созданной. Повторная доставка подтверждения/уведомления выполняется как отдельная персистентная задача, а не откатом брони.

## 7. Snapshot услуги

При подтверждении копируются:

- `service_name_snapshot`;
- `price_snapshot` как `Decimal`/`NUMERIC`, валюта RUB;
- `duration_min_snapshot`;
- `duration_max_snapshot`.

После создания эти поля не изменяются вслед за каталогом. При переносе новая связанная запись наследует snapshot старой записи, если клиент не меняет услугу; v0.1.0 не предлагает смену услуги внутри переноса.

## 8. Самостоятельная отмена

Дедлайн проверяется по UTC instant:

```text
allowed = appointment.start_at - now >= cancellation_deadline
```

Ровно за 36 часов действие разрешено. Операция в транзакции блокирует appointment и window, повторно проверяет владельца, статус и дедлайн, затем:

1. Ставит `cancelled_by_client`, `cancelled_at`, причину и status history.
2. Отменяет все несработавшие NotificationJob.
3. Если окно ещё в будущем и не помечено администратором к закрытию, переводит `booked -> open`; иначе — `closed`.
4. Пишет безопасное audit-событие.

Менее чем за deadline самостоятельное действие отклоняется с заданным текстом и кнопкой `https://t.me/example_studio`.

Администратор может отменить в любое время. UI администратора явно спрашивает, переоткрыть ли ещё будущее окно; прошедшее окно не переоткрывается.

## 9. Перенос

Самостоятельный перенос использует тот же deadline; администратор переносит независимо от него. Новое окно должно соответствовать услуге и всем обычным правилам доступности.

Транзакция:

1. Определяет локальные даты старого и нового окон.
2. Получает date advisory locks в сортированном порядке.
3. Блокирует оба окна по возрастанию ID и старую appointment.
4. Повторно проверяет право, статус старой записи, deadline, статус нового окна, вместимость и дневной лимит новой даты.
5. Создаёт новую Appointment `confirmed` со ссылкой на старую и со snapshot старой услуги.
6. Старую помечает `rescheduled`; её задания отменяет.
7. Старое будущее окно переоткрывает, новое делает `booked`.
8. Добавляет status history обеих записей и новые будущие NotificationJob.
9. Делает один commit.

Если любая проверка или запись не удалась, rollback сохраняет исходную запись и оба исходных состояния окон.

При переносе в другую дату дневной count новой даты проверяется без учёта старой записи. При переносе внутри одной даты старая активная запись исключается из count, поскольку она станет `rescheduled` в той же транзакции.

## 10. Напоминания

Для каждого включённого получателя и offset рассчитывается `scheduled_at = start_at - offset`. Задание создаётся только при `scheduled_at > now`; равное `now` уже не считается будущим.

Уникальный ключ не позволяет дважды создать один тип напоминания для одной записи и получателя. При отмене/переносе pending и processing задания переводятся в `cancelled`. Worker перед отправкой повторно проверяет актуальный статус записи и блокировку пользователя.

`processing` имеет lease. После смерти worker просроченный lease можно забрать повторно. Временные ошибки используют ограниченный exponential backoff, `RetryAfter` — указанную Telegram задержку с небольшим запасом, постоянный запрет отправки — `failed` и `User.is_blocked = true`. Полный exception text и payload сообщения в БД/лог не сохраняются.

Изменение reminder offsets пересоздаёт ещё не отправленные задания будущих активных записей; отправленные задания не повторяются.

## 11. Авторизация и владение

- Клиент получает и изменяет Appointment только с `appointment.client_id == current_user.id`.
- Admin use cases дополнительно проверяют Telegram ID по актуальной конфигурации; одного callback/DB role недостаточно.
- Сервис всегда повторяет проверку владения, даже если handler отфильтровал кнопку.
- Нельзя принять переданный Telegram contact другого пользователя, если у contact заполнен несовпадающий `user_id`; ручной телефон нормализуется и валидируется отдельно.

## 12. Проверяемые инварианты

Минимальный обязательный набор тестов:

1. Закрытое, занятое и просроченное окно не бронируется.
2. Две параллельные транзакции на одно окно дают ровно одну запись.
3. Параллельные записи разных окон не обходят дневной лимит.
4. Выходной, пересечение, недостаточный gap и выход за горизонт отклоняются.
5. `duration_max`, а не средняя/min длительность, должна помещаться в окно.
6. Изменение услуги не меняет snapshot существующей записи.
7. Клиентская отмена разрешена при `>= deadline` и запрещена при `< deadline`; admin не ограничен.
8. Перенос атомарен и при сбое не теряет старую бронь.
9. Отменённая/перенесённая запись не получает напоминаний; просроченные offsets не создаются.
10. Неадминистратор не вызывает admin use case, клиент не читает чужую запись.
