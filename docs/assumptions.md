# Спорные предположения и решения v0.1.0

Статус: рабочие решения, применённые в MVP v0.1.0. Изменение этих правил требует согласованного обновления кода, миграций, тестов и пользовательских текстов.

## Решения, принятые для проектирования

1. **Одно окно — одна запись.** Окно неделимо, остаток после более короткой процедуры повторно не продаётся. Проверяется только то, что `duration_max` услуги помещается в окно.
2. **Горизонт включителен по локальной дате.** Разрешены будущие окна от сегодняшней даты до `today + booking_horizon_days` включительно; время всегда должно быть строго в будущем.
3. **Настройка дневного лимита трактуется в двух местах.** ТЗ одновременно говорит о максимуме активных записей и о проверке количества окон при создании. В v0.1.0 `max_appointments_per_day` ограничивает активные окна (`open/reserved/booked`) при их создании и отдельно повторно ограничивает записи при бронировании. Закрытое/истёкшее окно лимит окон не занимает. Это буквальное и наиболее консервативное исполнение ТЗ, хотя оно не позволяет показать больше альтернативных времён, чем дневная ёмкость.
4. **Дневной лимит использованной ёмкости.** В count записей входят `confirmed`, `client_confirmed`, `completed`, `no_show`; отменённые и старые `rescheduled` не входят. Лимит вычисляется по локальной дате бизнеса.
5. **`reserved` не используется клиентским flow v0.1.0.** Между выбором в FSM и финальным подтверждением окно остаётся `open`; только транзакция решает гонку. Статус сохранён в enum для будущего короткого hold/предоплаты.
6. **Перенос создаёт связанную новую запись.** Старая получает терминальный `rescheduled`, новая — `confirmed`; добавляется nullable `rescheduled_from_id`/`rescheduled_to_id` либо эквивалентная связь. Это сохраняет историю лучше, чем перезапись `window_id`.
7. **Услуга при переносе не меняется.** Новая запись наследует snapshot старой. Смена услуги выполняется отменой и новой записью либо будет отдельным сценарием будущей версии.
8. **Переоткрытие после отмены.** Допустимая клиентская отмена автоматически открывает будущее окно. При административной отмене мастер выбирает `open` или `closed`. Занятое окно нельзя отдельно закрыть без обработки записи.
9. **Несколько будущих записей клиента разрешены.** ТЗ не устанавливает лимит на клиента; раздел «Моя запись» отображает список, если записей несколько.
10. **Деньги — российские рубли.** Хранение `NUMERIC(12,2)`/`Decimal`, отображение в ₽. Float запрещён.
11. **Цена может быть нулевой, но не отрицательной.** Это позволяет консультацию/бонусную услугу; при необходимости бизнес может установить минимальную положительную цену.
12. **Архив услуги — `is_active = false`.** Hard delete допустим только при отсутствии ссылок Appointment/Audit. Изменение или архив не затрагивает snapshots.
13. **Окна обычно не удаляются физически.** `closed` — стандартное архивное действие; hard delete доступен лишь для никогда не использованного окна и всё равно отражается в AuditLog.
14. **Администратор определяется только env-списком.** DB role может синхронизироваться для UI, но не даёт полномочий. Пустой список нужен для первого `/whoami`, при этом admin handlers полностью закрыты.
15. **Админские Telegram-уведомления возможны только после диалога с ботом.** Bot API не может первым написать пользователю. Уведомляются настроенные admin IDs, для которых уже существует доступный Telegram chat/user; недоступность фиксируется безопасно.
16. **Privacy URL обязателен для клиентского бронирования, но не для bootstrap.** При пустом URL `/whoami` работает, а consent/booking не запускаются. В production это считается ошибкой готовности конфигурации.
17. **Телефон не подтверждается SMS.** Telegram contact с совпадающим `user_id` считается наиболее надёжным источником; ручной номер нормализуется, но остаётся заявленным пользователем.
18. **Запрос удаления не означает немедленное физическое удаление всей истории.** До утверждения юридической политики бот принимает запрос, блокирует дальнейший маркетинг и позволяет администратору выполнить допустимую анонимизацию. Сроки хранения и состав обязательной истории требуют решения владельца/юриста.
19. **Изменение offsets обновляет будущие задания.** Pending/processing задания будущих активных записей пересчитываются; sent не создаются повторно, прошлые scheduled times пропускаются.
20. **Время начала является временем записи.** Отдельных `appointment.start_at/end_at` в минимальной модели нет; они берутся из связанного окна. Snapshot окна не меняется, а перенос создаёт новую запись.

## Ограничения, которые нельзя честно устранить только кодом бота

### Exactly-once отправка Telegram

Telegram `sendMessage` не принимает клиентский идемпотентный ключ. Если worker успешно отправил сообщение и умер до commit `sent`, повторная попытка может создать дубль; если заранее отметить `sent`, падение до отправки потеряет сообщение. Поэтому v0.1.0 гарантирует:

- персистентные задания;
- отсутствие обычных повторных захватов через lock/lease;
- уникальность задания;
- повтор временных ошибок;
- at-least-once с редким окном возможного дубля при аварийном завершении.

Строгое exactly-once не заявляется.

### Юридическая политика персональных данных

Технический privacy-документ не заменяет утверждённую политику, определение оператора данных, правового основания, сроков хранения и процедуры ответа на запрос удаления. До production-включения записи владелец должен предоставить опубликованный `PRIVACY_POLICY_URL` и согласовать текст.

## Вопросы, которые полезно подтвердить перед соответствующим этапом

1. Должен ли лимит `2` запрещать создание третьего альтернативного открытого окна или ограничивать только фактические записи? Сейчас выбрана строгая трактовка: запрещает и то, и другое.
2. Нужно ли разрешить клиенту больше одной будущей записи? Сейчас разрешено.
3. Должно ли окно автоматически открываться после клиентской отмены, или решение всегда остаётся мастеру? Сейчас при отмене за deadline оно открывается автоматически.
4. Допускается ли бесплатная услуга с ценой `0`? Сейчас допускается.
5. Какие сроки хранения и правила анонимизации должны применяться после запроса удаления данных? До юридического решения автоматическое уничтожение истории не проектируется.

## Подтверждённые решения для v0.2.0

Эти решения согласованы после аудита v0.1.0 и являются входом для реализации Этапов 2–9:

1. **Portfolio содержит не более 8 media.** Хранятся только Telegram `file_id`/`file_unique_id`; опубликованные работы архивируются, hard delete разрешён только для draft без значимых ссылок.
2. **Альбом broadcast получает отдельное сообщение с кнопками.** Media group несёт caption, а CTA отправляется следующим сообщением из-за ограничений Telegram Bot API.
3. **Работой делятся через deep link.** Inline mode не обязателен для v0.2.0.
4. **Списки используют limit/offset.** Каждый запрос имеет bounded page size, стабильную сортировку с `id` tie-breaker и проверку callback/page scope.
5. **Имена client/portfolio tags уникальны без учёта регистра.** В PostgreSQL это обеспечивается unique expression/index по `lower(name)`; slug portfolio tag также уникален.
6. **Лист ожидания не резервирует окно эксклюзивно.** Уведомляются все подходящие активные заявки, а первая успешная транзакция существующего `BookingService` побеждает.
7. **Повтор одного предложения запрещён парой request-window.** `UNIQUE(waitlist_entry_id, window_id)` дополняется cooldown для разных окон.
8. **Аудитория broadcast замораживается при явном подтверждении.** Непосредственно перед отправкой каждого recipient worker повторно проверяет marketing consent и доступность chat.
9. **Broadcast ограничен 15 сообщениями в секунду.** Один активный dispatcher защищён PostgreSQL advisory lock; recipient claims используют `SKIP LOCKED`, leases, RetryAfter и backoff.
10. **Broadcast feature flag по умолчанию выключен.** Его включают только после миграции и smoke test; тестовая отправка всегда ограничена администраторами.
11. **Repeat reminder планируется через 28 дней.** Он требует действующего marketing consent, отдельного repeat opt-out, отсутствия будущей записи и доступного Telegram chat.
12. **Внутренняя заметка имеет ограниченную длину и не логируется.** UI предупреждает о запрете медицинских, банковских и иных чувствительных данных; AuditLog хранит только метаданные действия.
13. **Hard delete не используется для опубликованных/исторических сущностей.** Portfolio, tags, notes, waitlist и campaigns используют status/archived timestamp; физическое удаление допустимо лишь для безопасного draft.
14. **Waitlist delivery не помещается в существующий `NotificationJob`.** Его appointment-oriented ограничения сохраняются; для pair entry-window используется отдельная надёжная очередь.
15. **Exactly-once Telegram delivery не обещается.** Уникальные задания, leases и terminal statuses дают практическую идемпотентность и at-least-once с документированным аварийным окном дубля.

Детальные модели, права, транзакционные границы, worker locks и последовательность миграций описаны в [architecture.md](architecture.md#16-архитектурное-расширение-v020-crm-и-маркетинг).
